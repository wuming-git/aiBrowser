# AI Browser 混合工具架构技术文档

> 文档目的：说明「后端控制面 + 桌面执行面」的混合工具架构，并记录已落地实现与联调方式。  
> 适用项目：`aiBrowserService`（LangChain4j）+ `aiBrowser`（Electron 桌面端）  
> 状态：**混合方案已实现（Phase 1–4）**

---

## 1. 背景与目标

当前后端已接入 **LangChain4j**，Agent 可通过 `@Tool` 调用服务端能力（如环境列表、指纹生成等）。  
业务演进后，Agent 还需要使用**桌面端独占能力**，例如：

| 能力类型 | 示例 | 为什么必须在前端/桌面端 |
|---------|------|------------------------|
| 浏览器控制 | 打开环境、导航、点击、输入、快照、截图 | 真实 Chrome Profile / 指纹 / 代理在本机 |
| 本地定时任务 | 每小时采集百度百科 | 依赖本机浏览器会话、本地调度、离线/常驻进程 |
| 部分前端接口 | 桌面端本地状态、本机缓存、扩展通信 | 数据或能力不在服务端 |

目标形态：

```text
用户任务
  → Agent（大脑，可在后端）
  → 选择并调用工具
      ├─ 后端工具（LangChain4j @Tool）
      └─ 前端/桌面工具（浏览器控制、本地定时任务、部分桌面 API）
```

同时必须满足：

1. **敏感接口不可被随意工具化**（防越权、防绕过）
2. **工具调用可审计、可追踪**
3. **尽量复用开源协议/库**，避免自研整套 Agent 协议

---

## 2. 你提出的两种方案

### 方案一：模型产出标准 JSON → 桌面端解析并本地发起

```text
云端/后端 Agent
  → 输出结构化计划（JSON：tool、args、order…）
  → 桌面端解析
  → 桌面端直接执行本地工具（浏览器 / 定时任务 / 本地 API）
```

**优点**

- 桌面能力完整：可直接控浏览器、跑本地 cron
- 延迟低：热路径不必每一步都回后端
- 实现直观，和「本地预处理小模型」可衔接

**缺点 / 风险**

- 若 JSON 由模型自由生成且桌面端信任执行，**等价于给模型本机执行权**
- 权限边界难做：哪些工具允许、参数是否合法、是否越权，全靠桌面端自己校验
- 与后端会话状态、用户权限、审计日志容易割裂
- 模型幻觉（捏造工具名/参数）需要桌面端强校验与白名单

**适合**

- 纯本机能力：浏览器 CDP、本地定时器、本地文件、本机扩展通信
- 已有严格 **Tool Catalog（白名单）+ Schema 校验 + 二次确认** 的场景

---

### 方案二：前端工具也通过后端接口暴露（后端代理/编排）

```text
Agent（后端 LangChain4j）
  → 调用后端 Tool
  → 后端鉴权 / 鉴权策略 / 审计
  → 若需要桌面能力：通过「会话通道」下发给在线桌面端执行
  → 桌面端回传结果给后端
  → 后端再返回给 Agent 继续推理
```

**优点**

- **权限与敏感接口统一收口**：JWT、RBAC、接口是否可工具化，由后端决定
- 审计完整：谁、何时、调了什么工具、参数与结果可落库
- 避免「模型直接打前端敏感 API」造成的绕过
- 与现有 LangChain4j Tool 模型一致，心智统一

**缺点**

- 必须有「桌面端在线通道」（WebSocket / 长轮询 / MQTT 等）
- 多一跳延迟；桌面离线时工具不可用
- 实现量比方案一略大（会话路由、超时、重试、结果关联）

**适合**

- 任何涉及账号、业务数据、计费、管理端能力的工具
- 需要合规审计、防越权的工具

## 3. 结论建议（推荐混合，而不是二选一）

> **推荐：方案二作为控制面（Control Plane），方案一仅作为本机执行面（Execution Plane）的实现细节。**

更准确地说：

| 层级 | 职责 | 采用思路 |
|------|------|----------|
| **控制面（后端）** | 工具注册、鉴权、是否允许调用、审计、编排 Agent | **方案二** |
| **执行面（桌面端）** | 真正操作浏览器、本地定时任务、本机 API | 类似方案一的「收标准调用指令并执行」 |
| **敏感接口** | 永不直接暴露给模型，也不暴露为桌面可任意调用的开放工具 | 后端白名单 + 参数校验 +（必要时）人工确认 |

即：

- Agent **只看到后端注册过的 Tool**（LangChain4j）
- 其中一部分 Tool 的实现是：`Backend Tool → 下发指令到 Desktop → Desktop 执行 → 回传`
- 桌面端**不接受模型原始自由文本当命令**；只接受后端签发的、符合 Schema 的 **ToolInvocation**

这样既保留方案二的安全边界，又保留方案一「桌面真正执行」的能力。

```text
┌─────────────────────────────────────────────────────┐
│ Backend (LangChain4j Agent)                         │
│  - 后端原生 Tool：listProfiles / generateFingerprint│
│  - 桌面代理 Tool：navigate / click / scheduleJob    │
│  - 权限：用户 JWT + Tool ACL + 审计日志              │
└───────────────────────┬─────────────────────────────┘
                        │ ToolInvocation (JSON Schema)
                        │ WebSocket / 会话通道
┌───────────────────────▼─────────────────────────────┐
│ Desktop (Electron)                                  │
│  - Tool Runtime：校验 schema → 执行 → 回传结果       │
│  - Browser tools / Local scheduler / Safe local API │
│  - 拒绝未注册、未授权、过期的调用                    │
└─────────────────────────────────────────────────────┘
```

## 4. 工具分类与安全策略

### 4.1 建议三类工具

1. **Server-Native Tools（后端原生）**  
   - 例：环境 CRUD 只读、指纹生成、用户配置查询  
   - 实现：LangChain4j `@Tool`，直接查库/调服务  

2. **Desktop-Proxied Tools（后端注册，桌面执行）**  
   - 例：`browser.navigate`、`browser.snapshot`、`scheduler.create`  
   - 实现：后端 Tool 内部发往在线桌面端  

3. **Forbidden / Human-Approved Tools（禁止或需确认）**  
   - 例：改密、支付、删除账号、导出全量 Cookie、任意本地 Shell  
   - 策略：不注册进 Agent；或注册但需 UI 二次确认 + 短时 token  

### 4.2 「前端接口当工具」的红线

**不应**把「所有前端 HTTP 接口」自动映射成工具。应：

- 显式维护 **Tool Manifest（白名单）**
- 每个工具声明：名称、描述、JSON Schema、所需权限、是否需桌面在线、是否敏感
- 敏感接口默认 **不进 Manifest**

## 5. 可复用的开源能力（优先复用）

### 5.1 强烈建议对齐的协议：MCP（Model Context Protocol）

- 官网/规范：[Model Context Protocol](https://modelcontextprotocol.io/)
- 价值：用标准方式描述「工具 / 资源 / 提示」，客户端与服务端解耦
- 对你们的映射建议：
  - **后端**：作为 Agent Host + 部分 MCP Server（业务工具）
  - **桌面端**：作为 **MCP Server**（browser / scheduler 工具集）
  - Agent 通过 Host 调用各 Server 的 tools（权限仍由 Host 控制）

相关实现：

| 组件 | 说明 |
|------|------|
| `@modelcontextprotocol/sdk` | 官方 TS SDK，适合 Electron 桌面端实现 MCP Server |
| LangChain4j MCP 支持 | 查当前版本是否已有 MCP client 集成；若有则优先用，避免自研 tool bridge |
| Claude/Cursor 生态 MCP 示例 | 可参考 tools list / call 的消息形状 |

> 即便暂时不全量上 MCP，也建议 **调用信封（envelope）直接采用 MCP 风格的 tools/call JSON**，便于以后无痛切换。

### 5.2 后端 Agent / Tool：继续 LangChain4j

- 已有：`AiServices` + `@Tool` + ChatMemory  
- 可扩展：
  - Tool Provider / 动态工具列表（按用户权限过滤）
  - 与 MCP Client 对接（若版本支持）把桌面工具动态挂入

参考文档：

- [LangChain4j Tools](https://docs.langchain4j.dev/tutorials/tools)
- [LangChain4j AiServices](https://docs.langchain4j.dev/tutorials/ai-services)
- [LangChain4j Spring Boot](https://docs.langchain4j.dev/tutorials/spring-boot-integration/)

### 5.3 浏览器自动化相关开源（桌面执行面）

| 库/项目 | 适用 | 备注 |
|--------|------|------|
| **Chrome DevTools Protocol (CDP)** / `chrome-remote-interface` | 控制已启动的带指纹 Chrome | 与现有「spawn Chrome + user-data-dir」最契合 |
| **Playwright** | 强大多，但更偏自管浏览器 | 若要坚持指纹定制内核/自启 Chrome，优先 CDP 挂接而非让 Playwright 另起浏览器 |
| **Puppeteer** | 同左 | 同上 |
| **browser-use**（Python） | Agent+浏览器范例多 | 架构可参考，但你们主栈是 Java+Electron，不建议整栈迁 Python |

你们现状更适合：**复用已有 Electron 启动的 Chrome，用 CDP/扩展注入执行工具**，而不是再引入一套完整 browser-use 运行时。

### 5.4 本地定时任务

| 库 | 说明 |
|----|------|
| **node-cron** / **croner** | Electron 主进程内轻量调度 |
| **agenda** / **bullmq** | 偏服务端队列，桌面端过重，除非以后有多机 worker |
| **OS 级任务计划** | 可做开机启动/补偿，但不适合细粒度「采集百科」循环 |

建议第一期：Electron 主进程 `croner`/`node-cron` + 任务元数据本地 SQLite/JSON；任务定义仍由后端签发/备案（便于审计与多端一致性）。

### 5.5 桌面 ↔ 后端实时通道

| 方案 | 说明 |
|------|------|
| **Spring WebSocket / STOMP** | 与现有 Spring Boot 一致，推荐 |
| **Socket.IO** | 前端生态熟，后端要额外适配 |
| **SSE + 客户端轮询回传** | 实现简单，双向能力弱，可作临时方案 |

推荐：Spring WebSocket，按 `userId + deviceId` 路由 ToolInvocation。

## 6. 推荐的标准调用格式（草案）

无论是否立刻上 MCP，建议统一 envelope：

```json
{
  "invocationId": "inv_01HXYZ...",
  "sessionId": "agent-session-...",
  "userId": 123,
  "deviceId": "desktop-xxx",
  "tool": "browser.navigate",
  "arguments": {
    "profileId": 1,
    "url": "https://baike.baidu.com/item/..."
  },
  "issuedAt": "2026-07-23T05:00:00Z",
  "expiresAt": "2026-07-23T05:02:00Z",
  "signature": "可选：后端HMAC/JWT"
}
```

桌面回传：

```json
{
  "invocationId": "inv_01HXYZ...",
  "ok": true,
  "result": {
    "title": "...",
    "url": "...",
    "snapshotRef": "local://..."
  },
  "error": null,
  "durationMs": 812
}
```

要点：

- **白名单 tool 名**
- **JSON Schema 校验 arguments**
- **短过期时间**（防止重放）
- **可选签名**（防伪造下发）

## 7. 场景示例：定时采集百度百科

### 7.1 一次任务编排（逻辑）

1. 用户：「每小时采集某词条摘要」  
2. 后端 Agent 规划：  
   - `scheduler.create`（周期 1h）  
   - 任务体包含步骤：`browser.openProfile` → `browser.navigate` → `browser.snapshot/extract` → `data.upload`  
3. `scheduler.create` 经鉴权后，下发到桌面端注册本地 cron  
4. 到点：桌面执行浏览器工具链，结果回传后端存储  
5. 若桌面离线：任务标记 pending，上线后补偿或告警

### 7.2 工具归属

| 步骤 | 工具 | 注册位置 | 执行位置 |
|------|------|----------|----------|
| 创建定时 | `scheduler.create` | 后端 | 桌面 |
| 打开环境 | `browser.launchProfile` | 后端 | 桌面 |
| 打开 URL | `browser.navigate` | 后端 | 桌面 |
| 抽取内容 | `browser.extractText` | 后端 | 桌面 |
| 保存结果 | `dataset.save` | 后端 | 后端 |

## 8. 与「本地小模型」的关系

现有 Electron 内嵌 llama.cpp 适合继续做：

- 敏感词预检  
- 关键词提取  
- **工具路由粗排（建议哪些 tool）**

但不建议让本地小模型**直接拥有执行权**。  
推荐链路：

```text
用户输入
  → 本地小模型：预检 / 建议 tools（可展示给用户）
  → 后端大模型 Agent：最终规划与正式 tool call
  → 后端鉴权后下发桌面执行
```

本地小模型是 **加速与防护层**，不是 **执行授权层**。

## 9. 方案对比总结

| 维度 | 方案一（桌面直执模型 JSON） | 方案二（后端工具代理） | 推荐混合 |
|------|---------------------------|----------------------|----------|
| 安全性 | 较弱，易越权 | 强 | 强（控制面在后端） |
| 桌面能力 | 强 | 需通道 | 强 |
| 审计 | 难统一 | 易统一 | 易统一 |
| 离线 | 可部分离线 | 依赖在线 | 可本地排队+上线同步 |
| 与 LangChain4j | 需额外协议 | 天然契合 | 契合 |
| 工程复杂度 | 中低 | 中高 | 中高（但边界清晰） |

**最终建议：采用混合架构——对外是方案二，对内桌面执行协议可复用方案一的 JSON 调用格式（最好对齐 MCP）。**

## 10. 落地状态与联调说明

> 原 Phase 规划已落地为**混合方案**实现。下文为当前代码状态（2026-07-23）。

### Phase 对照

| Phase | 内容 | 状态 |
|-------|------|------|
| 0 | LangChain4j Agent + Chrome 启动 + 本地小模型 | 已有 |
| 1 | Tool Manifest + ToolInvocation/Result + 审计 | **后端已完成** |
| 2 | `/ws/desktop` 通道 + deviceId + 心跳重连 | **已完成** |
| 3 | 人工行为浏览器工具集（puppeteer-core + ghost-cursor） | **已完成** |
| 4 | `scheduler.create/list/cancel`（croner） | **已完成** |
| 5 | MCP 化 | 未做（信封已对齐，可后续切换） |

### 关键路径

**后端 `aiBrowserService`**

- WebSocket：`/ws/desktop?token=&deviceId=`
- 网关：`DesktopToolGateway`（下发 invocation，等待 result，超时 90s）
- 工具：`BrowserAgentTools`（SERVER 原生 + DESKTOP 代理）
- HTTP：`GET /api/tools/manifest`、`GET /api/desktop/status`、Agent status 含 `desktopOnline`

**桌面 `aiBrowser`**

- 主进程：`electron/desktop/wsBridge.ts` 连接通道
- 执行：`electron/desktop/toolRuntime.ts`（白名单 + 过期校验）
- 人工浏览器：`electron/browser/humanSession.ts` + `humanTools.ts`
  - **puppeteer-core** `connect(browserURL)` 挂接已启动 Chrome
  - **ghost-cursor** 贝塞尔鼠标 / 犹豫点击
  - 逐字输入、分段滚轮、随机停顿
- 调度：`electron/desktop/scheduler.ts`（持久化到 userData）
- 登录进 Layout 后自动 `desktopConnect`；退出断开

### 联调步骤

1. 启动后端：`cd aiBrowserService && mvn spring-boot:run`（配置好 LangChain4j API Key）
2. 启动桌面：`cd aiBrowser && npm run dev`
3. 邮箱登录后，Agent 面板出现 **桌面 在线**（主进程日志 `[DesktopWS] online`）
4. 先创建至少一个浏览器环境
5. 对话示例：
   - 「列出环境，打开 id=… 的 https://example.com」→ `browser.open`
   - 「先 snapshot，再点击登录按钮」→ `browser.snapshot` → `browser.click`
   - 「在 #kw 输入关键词并回车」→ `browser.type` → `browser.pressKey`
   - 「提取页面文本」→ `browser.extractText`
   - 「每小时打开该 URL」→ `scheduler.create`（cron 如 `0 * * * *`）

### 安全边界（已落实）

- Agent **只调用**后端注册且 `enabled` 的工具
- 桌面 **只执行**后端下发的 `tool.invoke`，本地再做白名单与过期校验
- 本地小模型仍只做预处理，不直接执行工具

## 11. 风险清单

1. **提示注入**：页面内容诱导模型乱调工具 → 需工具白名单 + 结果净化 + 关键操作确认  
2. **桌面被恶意页面/扩展滥用** → 工具运行在主进程，校验来源只能是后端签发 invocation  
3. **长任务与上下文膨胀** → snapshot 要做精简（accessibility tree / 摘要），大内容存对象存储只回传引用  
4. **多设备同账号** → invocation 必须带 deviceId，避免下发到错误终端  
5. **模型幻觉工具** → 只允许 Manifest 内名称，未知 tool 直接拒绝  

---

## 12. 决策纪要（已确认）

1. **控制面放后端（方案二）**：所有 Agent 可见工具均由后端注册与鉴权。  
2. **执行面在桌面**：浏览器与本地定时任务由桌面执行，指令来自后端标准 JSON（可对齐 MCP）。  
3. **禁止「自动把前端接口变工具」**：仅白名单显式声明。  
4. **开源复用优先**：LangChain4j（Agent/Tool）+ MCP 思想/SDK + CDP 控已启动 Chrome + croner。  
5. **本地小模型**继续做预处理与建议，不直接授权执行。
