# 多智能体角色流水线（模板方法编排）技术文档

> 文档目的：在现有「后端控制面 + 桌面执行面」混合工具架构之上，设计一套**代码编排的多角色流水线**，提升 Agent 智能度与安全性。  
> 约束：**本文仅做方案设计，不修改现有代码。**  
> 适用项目：`aiBrowserService` + `aiBrowser`  
> 版本：v0.1 | 日期：2026-07-23

---

## 1. 背景与问题

当前 Agent 基本是「单模型一次对话 → 直接选 Tool → 下发桌面执行」：

```text
用户输入 →（可选本地预处理）→ 云端 Agent → Tool Call → 桌面执行 → 回复
```

短板：

| 问题 | 表现 |
|------|------|
| 单点决策过重 | 同一模型同时做理解、规划、风控、执行、验收，易漏步骤 |
| 流程可被绕过 | 若用 AI 自己决定「下一步找谁」，可能跳过风控角色 |
| 危险操作缺闸门 | 删除/编辑/敏感浏览器动作缺少分级授权 |
| 失败难恢复 | 工具链一旦跑偏，缺少统一回滚与验收重试 |
| 敏感检测靠云端 | 延迟高，且不宜把原始敏感文本全量上云 |

目标形态：

```text
用户目标
  → 【代码模板方法】固定顺序调度各角色
  → 各角色只做一件事（部分本地、部分云端、部分纯规则）
  → 工具执行前强制经过「敏感工具闸门」（纯代码）
  → 执行后验收；不达标则回滚并按策略重试
```

核心原则：

1. **编排权在代码，不在模型**（Template Method / Pipeline）
2. **角色职责单一**，输入输出契约明确
3. **风控分级**：中断 / 需授权 / 放行
4. **工具元数据强制**：至少声明「可否回滚」「是否幂等」
5. **能本地的尽量本地**（敏感词、工具敏感级、幂等校验）

## 2. 与现有架构的关系

不推翻混合工具方案，而是在其上加一层 **Role Pipeline**：

```text
┌──────────────────────────────────────────────────────────┐
│ Role Pipeline（模板方法，代码控制）                         │
│  Gate → Safety → Distill → Plan → AuthGate → Execute     │
│       → Observe → Verify → (Rollback?) → Reply           │
└────────────────────────────┬─────────────────────────────┘
                             │ 仍走现有通道
┌────────────────────────────▼─────────────────────────────┐
│ Backend Control Plane：Manifest / ACL / 审计 / LangChain │
│ Desktop Execution Plane：CDP + human tools / scheduler   │
└──────────────────────────────────────────────────────────┘
```

- 现有 Tool Manifest、WebSocket 下发、CDP 人工操作 **继续复用**
- 本地小模型（llama.cpp）可承接部分角色（敏感粗检、意图粗分）
- 新增的是：**角色定义、流水线状态机、授权 UI、回滚账本**

## 3. 角色总表

### 3.1 你提出的角色（保留并规范化）

| ID | 角色名 | 职责 | 建议运行位置 | 是否用 AI |
|----|--------|------|--------------|-----------|
| R1 | **操作风险官 RiskJudge** | 评估「接下来的操作 + 当前对话」危险系数，0–100 分 | 云端（可辅本地粗分） | 是（可+规则加权） |
| R2 | **内容安全官 ContentGuard** | 敏感词、敏感意图、涉政/涉黄等，0–100 分 | **优先本地**，必要时云端复核 | 本地规则/小模型为主 |
| R3 | **意图提炼官 IntentDistiller** | 把用户对话提炼成简洁目标与约束 | 云端或本地小模型 | 是 |
| R4 | **目标验收官 GoalVerifier** | 操作结束后判断是否达成目标；否则触发回滚/重开 | 云端 | 是 |
| R5 | **敏感工具闸门 ToolAuthGate** | 执行前按工具元数据判定是否需用户授权 | **纯代码（桌面或后端）** | **否** |

### 3.2 建议补充的角色

| ID | 角色名 | 职责 | 运行位置 | 是否用 AI |
|----|--------|------|----------|-----------|
| R0 | **会话秘书 SessionClerk** | 维护会话状态、消息窗口、授权票据、回滚点；不做决策 | 后端 | 否 |
| R6 | **计划官 Planner** | 把 R3 的目标拆成有序步骤（Step Plan），每步绑定候选工具 | 云端 | 是 |
| R7 | **观察官 Observer** | 执行前后采集页面快照/工具结果摘要，供验收与下一轮规划 | 桌面执行 + 后端压缩 | 可部分规则 |
| R8 | **执行官 Executor** | **唯一**允许真正发起 ToolInvocation 的角色（仍经 Manifest） | 后端代理 → 桌面 | 可选 AI 选参，但调用由代码发出 |
| R9 | **回滚官 RollbackOfficer** | 根据回滚账本逆序补偿；无法回滚则标记人工介入 | 后端编排 + 桌面/后端执行补偿工具 | 否（策略表驱动） |
| R10 | **授权官 ConsentBroker** | 向 UI 弹出授权卡、收集用户同意/拒绝、签发短时 ConsentToken | 桌面 UI + 后端校验 | 否 |
| R11 | **审计官 Auditor** | 全链路落库：角色分数、授权、工具、回滚结果 | 后端 | 否 |
| R12 | **策略官 PolicyEngine** | 静态策略：租户黑名单、时段限制、域名白名单、最大步数 | 后端纯代码 | 否 |

> 说明：R5 与 R10 分工——R5 判定「要不要授权」，R10 负责「怎么授权、授权是否仍有效」。

## 4. 评分与闸门规则（统一口径）

对 R1 / R2（及未来同类打分角色）统一：

| 分数区间 | 含义 | 流水线动作 |
|----------|------|------------|
| **≥ 80** | 极度危险 | **硬中断**：本轮停止，不进入规划/执行；记录审计；提示用户 |
| **60–79** | 高风险 | **需用户授权**：调用 R10；拒绝则中断；同意则签发短时票据后继续 |
| **< 60** | 可接受 | **直接放行**进入下一角色 |

建议补充：

- 分数必须附带 `reasons[]`（可解释），禁止只给一个数字
- R1 与 R2 **任一 ≥80 即中断**（取最严）
- R1 与 R2 任一落入 60–79：合并授权项一次弹出（避免连环弹窗）
- 本地 R2 可先做「快速否决」：命中硬敏感词表直接 ≥80，不必等云端

## 5. 模板方法编排（代码控制，禁止 AI 跳步）

### 5.1 为什么必须用代码编排

若让模型输出「下一步找角色 X」，会出现：

- 跳过 R1/R2
- 跳过 R5 直接执行删除类工具
- 假验收（自己说达成了）

因此采用 **Template Method / Pipeline**：

```text
abstract class AgentRoundTemplate {
  final run(ctx):
      R0.beginRound(ctx)
      R2.scan(ctx)                 // 可本地优先
      hardStopIfNeeded(ctx)        // ≥80
      R1.judge(ctx)
      hardStopIfNeeded(ctx)
      consentIfNeeded(ctx)         // 60–79 → R10
      R12.applyPolicy(ctx)         // 静态策略
      R3.distill(ctx)
      R6.plan(ctx)
      for step in plan:
          R5.precheck(step)        // 纯代码：工具敏感/幂等/回滚能力
          consentIfNeeded(ctx)     // 工具级授权
          R8.execute(step)         // 唯一执行出口
          R7.observe(step)
          R11.audit(step)
          if abortSignal: break
      R4.verify(ctx)
      if not achieved:
          R9.rollback(ctx)
          maybeRetry(ctx)          // 受最大重试次数约束
      R0.endRound(ctx)
}
```

要点：

- `run()` 是 `final`（概念上不可被子类改顺序）
- 角色以 **Hook / Strategy** 插入，可替换实现，**不能改调用顺序**
- AI 只出现在允许的 Hook 内部（R1/R2/R3/R4/R6 等），不能成为调度器

### 5.2 一轮会话的状态机

```text
IDLE
 → CONTENT_SCAN (R2)
 → RISK_JUDGE (R1)
 → CONSENT? (R10)
 → DISTILL (R3)
 → PLAN (R6)
 → STEP_LOOP:
      TOOL_GATE (R5) → CONSENT? → EXECUTE (R8) → OBSERVE (R7)
 → VERIFY (R4)
 → ROLLBACK? (R9)
 → DONE | ABORTED | NEED_HUMAN
```

非法迁移（如 DISTILL → EXECUTE 跳过 R5）在状态机层直接拒绝。

### 5.3 角色间数据契约（建议）

统一 `PipelineContext`（示意）：

```json
{
  "roundId": "rnd_...",
  "sessionId": "web-...",
  "userId": 123,
  "deviceId": "desktop-...",
  "userGoalRaw": "原始用户话",
  "scores": {
    "content": { "score": 12, "reasons": ["无命中"] },
    "risk": { "score": 35, "reasons": ["涉及打开外站"] }
  },
  "consent": {
    "tokens": ["ct_xxx"],
    "scopes": ["tool:browser.open", "risk:60-79"]
  },
  "distill": {
    "goal": "打开百度并搜索关键词 xxx",
    "constraints": ["不登录", "不提交表单"],
    "successCriteria": ["页面标题含关键词或结果列表可见"]
  },
  "plan": {
    "steps": [
      {
        "stepId": "s1",
        "tool": "browser.open",
        "args": { "profileId": 1, "url": "https://www.baidu.com" },
        "expect": "页面可访问"
      }
    ]
  },
  "observations": [],
  "toolLedger": [],
  "verify": { "achieved": false, "gap": "未看到搜索结果" },
  "status": "RUNNING"
}
```

每个角色只读写约定字段；禁止「自由发挥改全局」。

## 6. 各角色详细设计

### 6.1 R2 ContentGuard（本地优先）

**输入**：用户原文、可选本地预处理结果  
**输出**：`score` + `reasons` + `hits[]`

分层：

1. **字典/正则硬规则**（涉政、涉黄、暴恐、诈骗话术等）→ 可直接 ≥80  
2. **本地小模型**（现有 llama.cpp）做意图粗分  
3. （可选）云端复核：仅当本地 40–79 灰区时上送摘要，不上送全文（策略可配）

### 6.2 R1 RiskJudge

评估维度建议：

- 操作破坏性（删除环境、清数据、关进程）
- 资金/账号相关意图
- 越权（操作他人资源）
- 外联风险（未知域名、下载可执行文件）
- 与历史失败回滚次数叠加加权

可「AI 初评 + 规则加权封顶」，例如命中 `account.delete` 意图直接抬到 ≥80。

### 6.3 R3 IntentDistiller

产出必须结构化：

- `goal`（一句话）
- `constraints[]`
- `successCriteria[]`（可供 R4 检验的可观察标准）
- `outOfScope[]`（明确不做的事）

禁止输出可执行工具 JSON（避免越权到执行层）。

### 6.4 R6 Planner

把目标拆成步骤；每步：

- 绑定 **Manifest 内**工具名
- 声明依赖上一步 observation
- 预估是否需授权（供 UX 提前提示，最终仍以 R5 为准）

计划长度设上限（如 ≤12 步），防止无限循环。

### 6.5 R5 ToolAuthGate（纯代码，关键）

**禁止用模型决定「这个工具敏不敏感」。**

依据 Tool Manifest 扩展字段（见第 7 节）：

```text
if tool.authLevel == ALWAYS: requireConsent
if tool.authLevel == DESTRUCTIVE: requireConsent
if tool.authLevel == SENSITIVE && !hasConsent(scope): requireConsent
if !tool.rollbackable && policy.requireRollbackable: deny or requireConsent
if !tool.idempotent && step.retryCount > 0: deny or specialConfirm
```

输出只有三类：`ALLOW` / `NEED_CONSENT` / `DENY`。

### 6.6 R8 Executor

- 唯一调用 `DesktopToolGateway` / 服务端 Tool 的出口
- 执行前再次校验 ConsentToken（防重放、短过期）
- 每次执行写入 `toolLedger`（回滚账本）

### 6.7 R7 Observer

- 浏览器类：调用 `browser.snapshot` / `extractText` 精简版
- 结果做截断与脱敏后再进上下文，防提示注入与 token 膨胀

### 6.8 R4 GoalVerifier

对照 `successCriteria` + observations：

- `achieved=true` → 结束
- `achieved=false` → 输出 `gap` + 建议 `retryStrategy`（重试同计划 / 重规划 / 放弃）
- 严禁在本角色内直接调业务工具（只能建议，由模板方法决定是否 R9/R6）

### 6.9 R9 RollbackOfficer

- 按 `toolLedger` **逆序**执行补偿
- 仅对 `rollbackable=true` 的记录自动补偿
- 不可回滚项：标记 `NEED_HUMAN`，UI 提示用户手动处理
- 回滚本身也要审计

### 6.10 R10 / R11 / R12

- R10：桌面弹窗（危险说明、分数、将执行工具列表）→ 同意签发 JWT/随机 token（TTL 如 2 分钟，单次或限定 scopes）
- R11：全量审计，便于追责与复盘
- R12：最大轮次、域名白名单、夜间禁用删除等硬策略

## 7. 工具元数据：回滚与幂等（强制）

### 7.1 每个工具至少具备

| 字段 | 类型 | 含义 |
|------|------|------|
| `name` | string | 工具名（Manifest 唯一） |
| `rollbackable` | boolean | **是否支持回滚** |
| `idempotent` | boolean | **是否允许安全重复执行** |
| `authLevel` | enum | `NONE` / `SENSITIVE` / `DESTRUCTIVE` / `ALWAYS` |
| `sideEffect` | enum | `READ` / `WRITE` / `DELETE` / `EXTERNAL` |
| `compensationTool` | string? | 回滚时调用的补偿工具名 |
| `compensationFromResult` | boolean | 是否需用正向结果中的 ID 做补偿 |

示例：

| 工具 | rollbackable | idempotent | authLevel | 补偿思路 |
|------|--------------|------------|-----------|----------|
| `listProfiles` | true（无副作用） | true | NONE | 无需 |
| `browser.open` | 弱（可 close） | 条件幂等 | SENSITIVE | `browser.close` / 回到空白页 |
| `browser.click` | 多数 false | false | SENSITIVE | 难自动回滚 → 标 NEED_HUMAN 或页面级还原点 |
| `browser.type` | 条件 true | false | SENSITIVE | 清空输入或恢复旧值（需执行前快照） |
| `profile.update` | true | false | DESTRUCTIVE | 用更新前快照写回 |
| `profile.delete` | true（若软删）/ false（硬删） | false | ALWAYS | 软删可恢复；硬删需回收站 |
| `scheduler.create` | true | false | SENSITIVE | `scheduler.cancel` |
| `scheduler.cancel` | 条件 true | true | SENSITIVE | 需保留任务快照才能重建 |

### 7.2 「整段会话可回滚」的实现含义

不是魔法撤销一切，而是：

1. **执行前打检查点**（Checkpoint）：关键写操作前保存旧状态  
2. **账本记录**每次工具的：参数、结果、补偿所需数据、是否已补偿  
3. **逆序补偿**到本轮起点或最近检查点  
4. 对 `rollbackable=false` 的步骤：  
   - 规划阶段尽量避免；或  
   - 强制用户授权并提示「不可自动回滚」

浏览器 DOM 操作天然难完全回滚，建议策略：

- **环境级回滚**：回到导航前 URL / 关闭页签 / 重启 profile 会话  
- **数据级回滚**：仅对后端可逆资源（profile、scheduler job）做强保证  
- **验收失败默认**：优先「环境检查点还原」+「重规划」，而不是假装 DOM undo

### 7.3 幂等性规则

- `idempotent=true`：网络重试、流水线重入可直接再调  
- `idempotent=false`：重试必须换 `invocationId` 并经 R5；或改为调用补偿后再正向执行  
- Executor 层维护 `dedupeKey`（sessionId+stepId+attempt）防重复提交

## 8. 本地 / 云端部署划分

| 能力 | 本地桌面 | 云端后端 |
|------|----------|----------|
| R2 敏感词硬规则 | ✅ 主 | 可选复核 |
| 本地小模型预处理 | ✅ | — |
| R5 工具敏感闸门 | ✅ 可双端各跑一次 | ✅ 权威裁决建议在后端 |
| R10 授权 UI | ✅ | 校验 token |
| CDP 工具执行 | ✅ | 下发 |
| R1/R3/R4/R6 | 可选本地弱模型 | ✅ 主（强模型） |
| R0/R9/R11/R12 | 辅助 | ✅ 主 |
| 回滚账本权威存储 | 缓存 | ✅ 主 |

推荐：**后端是编排与权威状态机；桌面是执行器 + 本地快检 + 授权 UI。**  
即使桌面离线本地做了敏感拦截，上线后仍以服务端审计为准补记。

## 9. 与现有本地小模型、CDP 工具的衔接

```text
用户输入
  → 本地 R2（字典+llama）快速分
  → 若 <80：上送后端 Pipeline
  → 后端 R1 → R3 → R6
  → 每步 R5（代码）→（授权）→ R8 → Desktop humanTools
  → R7 snapshot/extract
  → R4 验收
  → 失败则 R9 +（可选）重新 R3/R6
```

现有 `browser.*` human tools 继续作为 R8 的执行后端；  
现有 `ToolManifest` 扩展 rollback/idempotent/authLevel 字段即可，不必新造协议。

## 10. 授权与人机协同 UX（要点）

授权弹窗至少展示：

- R1/R2 分数与 reasons  
- 即将执行的工具与参数摘要  
- 是否可回滚、是否幂等  
- 同意 / 拒绝 / 修改目标  

授权通过后：

- 写入 `ConsentToken(scopes, expireAt, roundId)`  
- R5/R8 校验；过期作废

## 11. 失败与重试策略

| 场景 | 策略 |
|------|------|
| R1/R2 ≥80 | 中断，不重试 |
| 用户拒绝授权 | 中断或回到 R3 让用户改目标 |
| 单步工具失败 | 若幂等可有限重试；否则 R9 局部补偿后 R6 重规划 |
| R4 未达成 | 回滚本轮 → 最多 N 次重规划（如 2）→ 仍失败则 NEED_HUMAN |
| 桌面离线 | 不进入 R8；提示上线 |

防止「验收失败 → 无限回滚重开」：必须有 `maxVerifyRetries`。

## 12. 风险与边界

1. **浏览器操作不可完全回滚**：需在产品文案与元数据上诚实标注  
2. **R4 幻觉说「已达成」**：验收应尽量对照可观察证据（snapshot 字段），必要时二次规则校验  
3. **提示注入**：页面文本进 Observer 前要隔离标签（如 `<<UNTRUSTED_PAGE>>`），禁止其指令进入 R5/R8  
4. **本地敏感词库维护成本**：需可更新词包；灰区再上云  
5. **多角色延迟**：流水线变长；可用「低风险快路径」——R1/R2 都 <40 且仅只读工具时跳过部分重规划，但 **不可跳过 R5**  
6. **角色过多导致工程复杂**：一期先落地 R0/R1/R2/R3/R5/R8/R4/R9/R10/R11
